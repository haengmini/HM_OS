# HM OS V1 Implementation Plan

> **For Hermes:** Use subagent-driven-development skill to implement this plan task-by-task.

**Goal:** 현재 Linux 서버의 Agent OS·로컬 Wiki/Obsidian·최근 문서·서버 상태를 2D 픽셀 오피스로 보여주고, Tailscale + HM OS PIN 인증 뒤 터미널과 파일을 전면 제어할 수 있는 Windows 중심 PWA를 구축한다.

**Architecture:** HM OS는 서버 중심의 단일 사용자 웹앱이다. React/TypeScript PWA가 픽셀 오피스와 제어 패널을 제공하고, Node.js API가 현재 Linux 사용자 권한으로 로컬 상태 수집·파일 작업·PTY 터미널을 수행한다. 외부 접속은 Tailscale Serve를 통해서만 허용하며, 백엔드는 Tailscale 사용자 신원과 HM OS PIN 세션을 모두 검증한다.

**Tech Stack:** TypeScript, React, Vite, PixiJS, Fastify, WebSocket, node-pty, SQLite, Vitest, Playwright, PWA service worker, Tailscale Serve, GitHub Actions

---

## 1. 확정된 V1 범위

### 사용자 경험

- 홈 화면은 **2D 픽셀 오피스**다.
- Windows 데스크톱·노트북을 우선 지원하는 설치형 PWA다.
- 모바일은 핵심 상태 확인과 잠금/해제가 가능한 반응형 화면까지 지원한다.
- 픽셀 오피스의 캐릭터·방·말풍선은 실제 서버 상태를 반영한다.
- 캐릭터나 방을 클릭하면 실제 상태, 최근 활동, 관련 파일을 연다.

### 실제 데이터

- 현재 Linux 서버의 프로세스·디스크·메모리·서비스 상태
- Agent OS 프로필과 작업 상태
- 로컬 Wiki/Obsidian 및 최근 문서
- 프로젝트·작업 데이터는 위 소스에서 확인 가능한 범위부터 연결

### 제어 범위

- V1 실행 대상은 **현재 Linux 서버 한 대**다.
- API와 명령은 현재 HM OS 서버 프로세스를 실행하는 Linux 사용자 권한으로 실행한다.
- 로그인 후 명령은 추가 승인 없이 즉시 실행한다.
- 파일 접근 범위는 해당 Linux 사용자가 접근 가능한 로컬 범위와 이미 인증된 서비스다.
- V1은 새 `sudo/root` 권한을 부여하지 않는다.
- Windows 원격 노드 제어는 V1 이후로 미룬다.

### 인증

1. Tailscale Serve가 전달한 사용자 신원과 Host를 검증한다.
2. HM OS PIN을 Argon2id 계열 해시로 검증한다.
3. 인증 성공 후 짧은 수명의 `HttpOnly`, `Secure`, `SameSite=Strict` 세션 쿠키를 발급한다.
4. 일정 시간 미사용 시 화면을 잠그고 PTY·파일 WebSocket을 종료한다.
5. 로그인 실패 횟수 제한과 감사 로그를 둔다.

### 저장소 정리

- 기존 연구 문서는 삭제하지 않는다.
- 원문은 `docs/legacy/`로 이동해 보존한다.
- 현재 README는 제품 README로 교체하고 기존 README도 legacy에 보존한다.
- 앱·테스트·운영 문서를 모노레포 구조로 재편한다.

## Milestone 1 — 인증·잠금·세션 보안 기반

**목표:** Tailscale 사용자와 HM OS PIN을 모두 통과한 세션만 앱과 API에 접근하게 한다.

**주요 파일**

- 생성: `apps/api/src/auth/tailscale-identity.ts`
- 생성: `apps/api/src/auth/pin.ts`
- 생성: `apps/api/src/auth/session-store.ts`
- 생성: `apps/api/src/auth/guards.ts`
- 생성: `apps/api/src/routes/auth.ts`
- 생성: `apps/web/src/features/auth/LockScreen.tsx`
- 생성: `packages/contracts/src/auth.ts`
- 테스트: `apps/api/src/auth/*.test.ts`
- 테스트: `tests/e2e/auth.spec.ts`

**보안 계약**

- 백엔드는 loopback에만 바인딩한다.
- 정확한 Tailscale Host와 사용자 로그인 헤더를 요구한다.
- 직접 loopback 개발 모드는 명시적 환경변수에서만 허용한다.
- PIN 원문은 저장하거나 로그에 남기지 않는다.
- 세션 쿠키는 스크립트에서 읽을 수 없게 한다.
- 잠금 시 모든 활성 PTY·파일 편집 채널을 종료한다.

**검증**

- 잘못된 Host·누락된 Tailscale 신원·잘못된 PIN은 403/401이다.
- 올바른 신원과 PIN은 세션을 만든다.
- 세션 만료와 수동 잠금 후 API 및 WebSocket이 거부된다.
- 반복 실패 rate limit이 작동한다.

**종료 기준**

- 인증 우회 테스트가 모두 실패한다.
- 실제 브라우저에서 잠금→해제→자동 잠금 흐름이 작동한다.

**기능**

- 여러 터미널 탭과 세션 복원 가능한 메타데이터
- 파일 탐색, 읽기, 편집, 생성, 이동, 업로드, 다운로드

**안전 구현 원칙**

- 브라우저가 Hermes의 범용 에이전트 API나 호스트 도구 API를 직접 호출하지 않는다.
- 모든 WebSocket 연결에서 유효한 HM OS 세션을 재검증한다.
- 명령·파일 내용·토큰 원문은 감사 로그에 저장하지 않는다.
- 서버 프로세스의 Linux 사용자 권한을 넘지 않는다.
- 잠금·로그아웃·세션 만료 시 PTY를 종료하거나 명시적 정책에 따라 분리한다.
- PIN과 서비스 토큰은 프런트엔드 번들에 포함하지 않는다.

**검증**

- 실제 터미널에서 `pwd`, 테스트 실행, 장기 명령, Ctrl+C, resize가 작동한다.
- UTF-8·한글 파일명과 대용량 로그 일부 읽기가 작동한다.
- 동시 파일 수정 충돌을 감지한다.
- 인증 없는 HTTP/WebSocket 요청으로 명령을 실행할 수 없다.
- 화면 잠금 직후 기존 터미널 채널이 차단된다.

**종료 기준**

- Windows 브라우저에서 서버 터미널과 파일 작업을 실제로 완료할 수 있다.

## Milestone 5 — PWA·Tailscale·운영 배포

**목표:** 여러 개인 기기에서 비공개 HTTPS 주소로 설치하고 안정적으로 재접속할 수 있게 한다.

**주요 파일**

- 생성: `apps/web/public/manifest.webmanifest`
- 생성: `apps/web/src/sw.ts`
- 생성: `docs/operations/INSTALL.md`
- 생성: `docs/operations/TAILSCALE.md`
- 생성: `docs/operations/BACKUP_AND_RECOVERY.md`
- 생성: `scripts/start-hm-os.sh`
- 생성: `scripts/healthcheck.sh`
- 생성: 사용자 서비스 정의 또는 검증된 프로세스 supervisor 설정
- 생성: `.github/workflows/ci.yml`
- 생성: `.github/workflows/release.yml`

**배포 방식**

- API는 `127.0.0.1`에만 바인딩한다.
- Tailscale Serve가 HTTPS와 신원 헤더를 담당한다.
- 서버 전체 제어가 필요하므로 V1 API는 호스트의 비권한 사용자 서비스로 실행한다.
- 컨테이너에 Docker socket이나 서버 루트를 광범위하게 마운트하는 방식은 사용하지 않는다.
- GitHub Actions는 build/test/release artifact까지만 자동화한다.
- 실제 서버 버전 전환은 승인된 릴리스에 대해서만 수행한다.

**검증**

- tailnet 밖에서는 접속할 수 없다.
- 올바른 사용자만 Tailscale 신원 검증을 통과한다.
- Windows에서 PWA 설치·재실행·업데이트가 작동한다.
- 모바일에서 잠금 화면과 상태 조회가 작동한다.
- 서버 재시작 후 앱과 세션 정책이 문서대로 복구된다.
- 이전 버전으로 롤백할 수 있다.

**종료 기준**

- 최소 두 대의 개인 컴퓨터에서 동일한 실제 상태와 제어 기능을 사용한다.

## Milestone 6 — V1 통합 검증과 첫 릴리스

**목표:** 보안·기능·반응형·운영 복구를 통합 검증하고 `v0.1.0` 후보를 만든다.

**검증 매트릭스**

- 인증: 올바른/잘못된 Tailscale 사용자, PIN, 만료, 자동 잠금
- 상태: 서버·Agent OS·Wiki·최근 문서 정상/오류/오래됨
- 픽셀 오피스: 캐릭터 상태 변화, 상세 패널, 빈 상태
- 터미널: 일반 명령, 장기 명령, 인터럽트, 재접속, 잠금
- 파일: 읽기·편집·생성·이동·업로드·다운로드·충돌
- PWA: 설치, 새 버전 반영, offline shell, 온라인 API 복귀
- 화면: Windows Chrome/Edge, 1440×900, 1920×1080, 390px 모바일
- 운영: 프로세스 재시작, 데이터베이스 백업/복구, 릴리스 롤백

**필수 명령**

```bash
npm run lint
npm run typecheck
npm test
npm run build
npm run test:integration
npm run test:e2e
```

**종료 기준**

- blocker/critical 결함 0개
- 인증 우회 0개
- 실제 서버 상태와 UI 상태가 일치
- 두 대 이상의 기기에서 설치·로그인·터미널·파일 작업 검증
- 릴리스 노트와 알려진 한계 작성
- 사용자 승인 후에만 태그·GitHub push·서버 배포

## 4. 마일스톤별 사용자 검토 게이트

| 게이트 | 확인할 내용 | 외부 변경 |
|---|---|---|
| G0 | 저장소 재구성·아키텍처·보안 계약 | 없음, 로컬 작업만 |
| G1 | 잠금 화면과 인증 흐름 | 없음, 로컬 실행 |
| G2 | 실제 데이터가 올바르게 표시되는지 | 없음, 읽기 전용 연동 |
| G3 | 픽셀 오피스 시각 방향 | 없음, 로컬 프리뷰 |
| G4 | 터미널·파일 전면 제어 UX | 로컬 서버 제어 발생 |
| G5 | Tailscale 비공개 배포 | 서버 서비스·네트워크 설정 변경 |
| G6 | `v0.1.0` 릴리스 | GitHub push/tag/release 및 배포 |

각 게이트에서 실제 화면·테스트 결과를 제시한다. GitHub push, 태그, 릴리스, Tailscale 설정 변경, 서버 서비스 등록은 사용자 승인 전에는 실행하지 않는다.

## 5. 주요 위험과 대응

### R1. 로그인 후 즉시 전면 제어

- **위험:** 세션 탈취나 열린 브라우저가 곧 서버 계정 탈취로 이어질 수 있다.
- **대응:** Tailscale 신원 + HM OS PIN, 짧은 세션, 자동 잠금, WebSocket 재검증, loopback-only origin, rate limit, 감사 로그.

### R2. 브라우저 기반 PTY 구현

- **위험:** 장기 프로세스, reconnect, resize, 제어문자 처리에서 오류가 날 수 있다.
- **대응:** node-pty 기반 통합 테스트, 잠금 시 수명 정책 명시, synthetic shell 대신 실제 PTY smoke test.

### R3. Agent OS 상태 형식이 일정하지 않을 수 있음

- **위험:** 파일·프로세스·세션 소스가 서로 다른 상태를 말할 수 있다.
- **대응:** adapter 계층에서 출처·시각·신뢰도를 보존하고 `stale/unknown`을 명시한다.

### R4. 픽셀 UI가 장식으로 끝날 위험

- **위험:** 예쁘지만 실제 통제에 느린 화면이 될 수 있다.
- **대응:** 모든 방·캐릭터를 실제 상태와 패널에 연결하고, 검색·목록 보기 대체 UI도 제공한다.

### R5. Tailscale 실행 환경 미확인

- **현 상태:** 현재 shell에서 `tailscale` 명령은 발견되지 않았다.
- **대응:** Milestone 5 전에 실제 daemon/사용자 모드 설치 상태와 tailnet 신원을 별도로 조사하고, 시스템 변경은 승인을 받은 뒤 수행한다.

## 7. 착수 순서

1. 이 마일스톤 문서를 사용자와 합의한다.
2. Milestone 0만 구현한다.
3. 로컬 diff, 파일 이동 해시, lint/typecheck/test 결과를 검토한다.
4. G0 승인 후 Milestone 1로 이동한다.
5. 이후 각 마일스톤을 구현 → 테스트 → 시각 검토 → 다음 게이트 순서로 진행한다.

첫 구현 범위는 **Milestone 0만**이며, 원격 저장소에는 아직 push하지 않는다.
